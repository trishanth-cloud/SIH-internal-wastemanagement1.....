# E-Waste Tracker — System Architecture & Database Schema
Stack: HTML/CSS/JavaScript + Firebase (Auth, Firestore, Storage, Hosting)

## 1. What the app needs to do (scope for a hackathon)

Keep the MVP tight:
- Users sign up / log in
- Users log an e-waste item (type, weight/quantity, photo, pickup location)
- Users see status of their submissions (Pending → Scheduled → Collected → Recycled)
- Admin/collector view to update status
- A dashboard showing total e-waste diverted (nice-to-have, great demo value)

Cut anything else if you're short on time — payment, route optimization, gamification, etc. can be "future work" slides.

## 2. High-level architecture

```
┌─────────────────────────────┐
│      Browser (Client)       │
│  index.html / dashboard.html│
│  style.css                  │
│  app.js, auth.js, db.js     │
└──────────────┬───────────────┘
               │ Firebase SDK (client-side, no custom backend needed)
               ▼
┌─────────────────────────────────────────────┐
│                Firebase Project              │
│                                               │
│  ┌───────────────┐   ┌──────────────────┐    │
│  │ Firebase Auth │   │ Cloud Firestore  │    │
│  │ (email/pass   │   │ (NoSQL database) │    │
│  │  or Google)   │   │                  │    │
│  └───────────────┘   └──────────────────┘    │
│                                               │
│  ┌───────────────┐   ┌──────────────────┐    │
│  │ Firebase       │   │ Firebase Hosting │    │
│  │ Storage        │   │ (deploy static   │    │
│  │ (item photos)  │   │  site free)      │    │
│  └───────────────┘   └──────────────────┘    │
└─────────────────────────────────────────────┘
```

Why this shape works for a hackathon:
- No custom backend server to write, deploy, or debug — Firebase's client SDK talks directly to Auth/Firestore/Storage.
- Firestore's security rules act as your "API authorization layer" instead of writing Express routes.
- Firebase Hosting gives you a live URL to demo in under 5 minutes.

## 4. Step-by-step build order

**Step 1 — Firebase project setup**
1. Create a project at the Firebase console.
2. Enable Authentication (Email/Password, or add Google sign-in).
3. Create a Firestore database (start in test mode for hackathon speed, then tighten rules before demo day).
4. Enable Storage (for item photos).
5. Copy your Firebase config snippet into `js/firebase-config.js`.

**Step 2 — Auth flow**
1. Build a simple signup/login form in `index.html`.
2. In `auth.js`, use `createUserWithEmailAndPassword` and `signInWithEmailAndPassword`.
3. On successful login, create/update a `users` document in Firestore (see schema below) and redirect to `dashboard.html`.
4. Use `onAuthStateChanged` on every protected page to guard access and get the current user's UID.

**Step 3 — Submit an e-waste item**
1. Form fields: item type, quantity/weight, description, photo, pickup address.
2. On submit: upload photo to Storage → get download URL → write a document to the `ewasteItems` collection (schema below) with `status: "pending"`.

**Step 4 — User dashboard**
1. Query Firestore for `ewasteItems` where `userId == currentUser.uid`, ordered by `createdAt desc`.
2. Render as cards/table showing status badges.
3. Use `onSnapshot` (real-time listener) instead of a one-time `get()` so status updates reflect live — great for demos.

**Step 5 — Admin/collector view (optional but impressive)**
1. A simple page listing all items with status `pending` or `scheduled`.
2. Buttons to advance status (`pending → scheduled → collected → recycled`).
3. Restrict this page using a `role` field on the user's document + Firestore rules.

**Step 6 — Impact dashboard (great demo closer)**
1. Aggregate stats: total items recycled, estimated kg diverted, items by category.
2. Simplest approach for a hackathon: read all `ewasteItems` with `status == "recycled"` client-side and sum in JS. (A Cloud Function-based aggregate counter is more "production," but skip it unless you have time.)

**Step 7 — Deploy**
1. `npm install -g firebase-tools`
2. `firebase login`
3. `firebase init hosting`
4. `firebase deploy`

## 5. Database schema (Firestore — NoSQL, collection/document model)

Firestore isn't relational, so think in terms of collections of documents rather than tables with joins.

### Collection: `users`
Document ID = Firebase Auth UID

| Field | Type | Notes |
|---|---|---|
| `name` | string | |
| `email` | string | |
| `role` | string | `"user"` or `"admin"` |
| `phone` | string | optional |
| `createdAt` | timestamp | |

### Collection: `ewasteItems`
Document ID = auto-generated

| Field | Type | Notes |
|---|---|---|
| `userId` | string | references `users` doc ID (UID) |
| `itemType` | string | e.g. `"laptop"`, `"phone"`, `"battery"` |
| `category` | string | e.g. `"IT equipment"`, `"small appliance"` — useful for the dashboard aggregation |
| `quantity` | number | |
| `estimatedWeightKg` | number | optional, used for impact stats |
| `description` | string | |
| `photoUrl` | string | download URL from Storage |
| `pickupAddress` | string | |
| `pickupLat` / `pickupLng` | number | optional, if you add a map |
| `status` | string | `"pending"` \| `"scheduled"` \| `"collected"` \| `"recycled"` |
| `statusHistory` | array of maps | `[{status, timestamp}]` — nice for an activity timeline |
| `createdAt` | timestamp | |
| `updatedAt` | timestamp | |

### Collection: `pickups` (optional, if you want scheduling as its own entity)

| Field | Type | Notes |
|---|---|---|
| `itemIds` | array of strings | references multiple `ewasteItems` |
| `collectorId` | string | references `users` doc (admin/collector) |
| `scheduledDate` | timestamp | |
| `status` | string | `"scheduled"` \| `"completed"` \| `"cancelled"` |

Skip this collection for MVP — fold pickup scheduling into `ewasteItems.status` unless a judge specifically asks about logistics.

### Why this shape (not a relational schema)
- No joins needed for the main dashboard query — just filter `ewasteItems` by `userId`.
- Denormalize where it saves you a lookup: e.g. you could store `userName` directly on `ewasteItems` so the admin table doesn't need a second query per row.
- Firestore charges per document read, so for a hackathon demo this barely matters — optimize for dev speed, not cost.

## 6. Minimal security rules (tighten before your demo)

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    match /ewasteItems/{itemId} {
      allow read: if request.auth != null &&
        (resource.data.userId == request.auth.uid ||
         get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == "admin");
      allow create: if request.auth != null && request.resource.data.userId == request.auth.uid;
      allow update: if request.auth != null &&
        get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == "admin";
    }
  }
}
```

This lets users see only their own items, while admins can see and update everyone's.

## 7. Fast wins for judging
- Real-time `onSnapshot` listeners make status changes feel "live" — good demo moment (change status in admin view, watch it update in user view in a second window).
- The impact dashboard (total kg/items recycled) gives judges a tangible "so what."
- Firebase Hosting deploy takes minutes, so you can demo from a real URL instead of localhost.
